# Reproducible upstream builds

The Soroswap pair and factory depend on the local `soroswap-factory-interface` crate. Cargo includes path dependency identities in generated crate identifiers, which changes WASM function/type ordering when the absolute checkout path changes. The pinned sources, lockfiles and artifact sizes stayed identical, but builds in the original workstation directory, GitHub runner directory and an independent clean checkout produced different pair/factory hashes. Token, router and DeFindex vault bytes matched across those builds. This is a build-path finding, not evidence that different WASM bytes are interchangeable in a code-pinned deployment.

`build-upstream.py` builds unchanged pinned sources under the fixed absolute `/tmp/mierkhat-upstream-v1` directory. The directory must be owned by the current user with mode `0700`, and an owned no-follow file lock serializes builds. Source HEAD and clean Git state are checked before building. Locked dependency versions and Rust 1.91.0 remain fixed. The script writes build output and its generated manifest into the requesting project's ignored `artifacts/` directory.

`evidence/upstream-build.json` is the historical deployed build record and is preserved byte-for-byte. `evidence/upstream-reproducible.json` separately pins the canonical build outputs. Verification compares the newly generated manifest with the canonical record, checks the actual WASM bytes, and requires source repository/revision, Cargo lock and sizes to agree with the historical record. The guard and migration still have to reproduce their original deployed hashes. CI tests those executables with freshly built upstream WASM and publishes both build records with source/checksum provenance.

The canonical pair/factory outputs are distinct artifacts. CI does not update testnet code, runtime profile pins or the packed SDK, and no equivalence or onchain compatibility is inferred merely from equal sizes or common source. Any deployment of a different upstream executable needs a separately reviewed profile and network evidence. The current API/frontend continue to use the existing reviewed deployment registry.
